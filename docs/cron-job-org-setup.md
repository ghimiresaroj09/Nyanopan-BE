# cron-job.org setup sheet

Two jobs: one keeps the Render instance awake, one runs real cleanup work.
Ping `/api/health/live/` for the keep-alive — **not** `/api/health/`: the
database-backed probe would pin the Neon compute awake all month and burn its
free compute allowance (details in the README).

## Gather these two values first

| Value | Where |
| --- | --- |
| `SERVICE_URL` | Render Dashboard → your service → the URL at the top of the page, e.g. `https://ecommerce-api.onrender.com` (Render appends a suffix if the name is taken) |
| `CRON_SECRET` | Render Dashboard → your service → **Environment** → `CRON_SECRET` (generated by `render.yaml`); click the eye icon to reveal, then copy |

## Job 1 — keep-alive (`warm-up`)

1. Sign in at <https://console.cron-job.org/>.
2. Click **Create cronjob** (top of the job list).
3. **Title**: `warm-up`
4. **Address / URL**: `SERVICE_URL` + `/api/health/live/`
   → e.g. `https://ecommerce-api.onrender.com/api/health/live/`
   Use the trailing slash and `https` exactly.
5. **Schedule**: choose the every-10-minutes preset if offered; otherwise use
   the cron-expression ("expert") mode and enter `*/10 * * * *`.
   Leave the timezone at UTC — this job does not care.
6. **Request method**: `GET`. No body, no headers.
7. Enable **failure notification** so you also get free downtime alerting.
8. **Save**.

## Job 2 — daily cleanup (`token-cleanup`)

1. **Create cronjob** again.
2. **Title**: `token-cleanup`
3. **Address / URL**: `SERVICE_URL` + `/api/v1/internal/cron/tokens/`
4. **Schedule**: `0 3 * * *` = 03:00 daily.
   **Set the timezone explicitly** — cron-job.org schedules in the job's
   timezone (account default). UTC 03:00 ≈ 08:45 in Kathmandu; pick
   `Asia/Kathmandu` if you want it to mean local 03:00.
5. **Request method**: `POST`. Body: leave empty.
6. **Headers**: add one entry —
   name `X-Cron-Secret`, value *the secret you copied from Render*.
   (If your editor shows one free-text box instead of name/value rows,
   write `X-Cron-Secret: <secret>` on a single line.)
7. Optional: **Save responses** on, so the history shows the JSON result.
8. **Save**.

## Verify it worked

- **Job 1**: open the job → **Run now** / **Test run**. Expect HTTP `200` and
  body `{"status": "alive"}`. Once it passes, the schedule keeps the instance
  warm.
- **Job 2**: press **Run now** and check the response body:
  ```json
  {"status":"success","message":"Cron job 'tokens' completed.","statusCode":200,
   "data":{"job":"tokens","expired_tokens":0,"blacklist_entries":0}}
  ```
  `expired_tokens: 0` is the normal result — it only counts rows that had
  accumulated.

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| First keep-alive run fails, later ones pass | Cold start takes ~1 min but cron-job.org gives up after 30 s. Open the URL in a browser once to wake the instance, then let the schedule hold it. The failure counter resets on the next success. |
| Job 2 returns `403` | `X-Cron-Secret` is missing or doesn't match `CRON_SECRET` in Render. Re-copy it (no stray spaces/newline). |
| Job 2 returns `503` | `CRON_SECRET` is unset or shorter than 16 characters on the Render service — the endpoints fail closed. |
| Job 2 returns `404` | Wrong path — it is `/api/v1/internal/cron/tokens/`, with the trailing slash. |
| Job disappears from the list | cron-job.org auto-disables a job after **25 consecutive failures**. Open the job → *Last executions* to see why. |
| Job 1 returns `301`/`302` | The URL dropped the trailing slash (`/api/health/live` → redirect). Use the trailing slash. |

## Notes

- cron-job.org requests come from a fixed IP set (`116.203.134.67`,
  `116.203.129.16`, `23.88.105.37`, `128.140.8.200`, `91.99.23.109`). Render's
  free plan has no IP allow-listing, so the shared secret — not the source IP —
  is what protects Job 2.
- The console can also import jobs via its REST API (Settings → API key), if
  you would rather script both jobs than click through the wizard.
